# 架构说明

内核由四层组成，自底向上：基础、实体与协议、编排、接口。每层只引用下面的层。本文说明其中三个核心抽象：计划图的数据结构、智能体类层次、节点协议，以及它们在运行时怎样连起来。

## 计划图

一个项目由一张计划图驱动。计划图由四个实体类表示（`indeterminate.plan`），每个类检查自己的字段，`Plan` 检查只有整张图才能判断的内容（引用是否存在、依赖是否成环）。

```text
Plan
├─ task        任务说明（可选）
├─ nodes       Node 列表
├─ edges       Edge 列表
└─ blocks      Block 列表
```

| 实体 | 必需字段 | 可选字段 | 含义 |
|---|---|---|---|
| `Node` | `id`、`name`、`summary`、`role` | `duty`、`block`、`accept`、`reads`、`tools`、`model`、`thinking`、`helpers`、`kind` | 图中的一个位置。`role` 决定由哪个智能体类运行，`kind` 决定运行的是哪种节点 |
| `Edge` | `id`、`from`、`to`、`kind`、`start`、`label` | | 从 `from` 到 `to` 的信息流。`kind` 是 `deliverable`、`review`、`feedback`、`rework` 之一；`start` 为真时也是启动依赖 |
| `Block` | `id`、`name`、`after` | `coordinator` | 一起放行的一组节点。`after` 里的任务块都放行后才能开始；`coordinator` 指向协调它的次主控节点 |

规则：

- `id` 为 `lead` 的节点是主控，不属于任何任务块，调度器不启动它。其他节点都属于一个任务块。
- 反馈边可以成环；启动依赖和任务块依赖不能成环。
- 实体从存档读出后再写回，得到的是逐字相同的定义，所以操作者确认过的计划摘要（`Plan.hash`，规范化 JSON 的 SHA-256）始终对应同一张图。

## 智能体类层次

所有模型实例都属于 `Agent` 类（`indeterminate.agents.kinds`）：

```text
Agent
├─ Coordinator          可以派生和跟进下属
│  ├─ Lead              项目主控：放行任务块、申请改图、批准助手
│  └─ SubLead           协调一个任务块，不能放行
├─ Worker               在自己的工作目录完成工作，可运行代码
├─ Reviewer             检查交付并写出意见，不运行代码
└─ Keeper               图外只读，只决定额外文件申请
```

类只声明能力和边界：默认工具、必需工具、是否协调他人、是否是主控、能否被派生、思考层级。它不规定模型怎么思考。运行时和图引擎通过询问能力做判断（"它能放行任务块吗"），从不比较角色名。

使用方继承这些类来定义自己的角色（例如 `class Translator(Worker)`），通过 `Extension` 注册。主控和文件处理两种能力只属于内核自己的 `Lead` 和 `Keeper`，注册的子类不能声明。

## 节点协议

调度器决定节点何时可以运行；节点种类决定运行什么（`indeterminate.graph.nodes`）。

一个节点满足以下条件时可以运行：计划已确认，所在任务块的前置任务块都已放行，所有启动边的上游节点都已提交。调度器为它预留一个实例，即编号的轮次 `nodes/<节点>/r<N>/`，内含 `work/`、`submit/`、`state/` 三个目录，然后交给节点种类：

```text
NodeKind
├─ check(node)                         起草计划时对该种类节点的额外检查
├─ prepare(graph, node, instance)      创建运行者（尚未运行），返回句柄
├─ activate(graph, handle)             开始运行；崩溃恢复后会再调用，所以必须幂等
├─ rework(graph, handle, reason)       主控要求返工
└─ stop(graph, handle, reason)         主控结束该实例
```

内核只内置一种：`agent`，即一个模型实例，它的 `role` 决定它是哪个智能体类。其他种类（程序运行、外部输入、设备读数等）由使用方继承 `NodeKind` 并注册到 `NodeKinds`，计划里用节点的 `kind` 字段指定。引擎未注册的种类不会启动。

不论哪种节点，交付都经过同一道检查：`GraphRun.submit` 核对文件、把它们快照到 `submit/` 并记录哈希。交付从不放行任务块，放行只由主控做。

## 一个项目的生命周期

1. 起草：使用方的任务类型（`TaskType.build_plan`）或主控生成计划草稿。草稿不会启动任何节点。
2. 确认：操作者核对计划摘要后确认。内核不会自动确认。
3. 调度：调度器按上面的条件挑出可运行的节点，交给各自的节点种类。
4. 交付：节点提交后，下游节点的启动依赖得到满足。
5. 放行：主控验收一个任务块后放行它，后续任务块才能开始。
6. 改图：主控申请修改计划，操作者批准后由主控应用。受影响的已有交付保留历史并暂停下游新启动，等待复核。
7. 恢复：所有状态都写在项目目录里。进程被强杀后用同一工作区重启即可续接，已启动的轮次不会重复启动。

## 边界

- 每个节点只能写自己本轮的 `work/`，只能读计划授权的输入。`submit/`、`state/` 和项目根目录下的系统文件由程序维护。
- 额外的文件读取由图外只读的 `Keeper` 逐个决定，授权由程序记录。
- 这些都是程序层面的路径与权限检查，不是操作系统隔离。

## 代码位置

| 层 | 目录 |
|---|---|
| 1 基础 | `core/`（事件、git、锁、项目存储、设置、沙箱）、`host.py`、`agents/providers.py` |
